# 开发流程与文档更新规则

> 状态：生效中
> 摘要：从领需求到提交的流程、提交信息规范，以及每一步该动哪个文档

---

## 0. 每次开工

1. 读 [NOW.md](NOW.md)——它写的就是当前事实，包括"改到一半没验证"。
2. 需要背景时查 [INDEX.md](INDEX.md) 定位相关 ADR 和设计文档。
3. 不要凭代码或印象推测项目进度。

## 1. 需求

改动需求 → 更新 [projectneed.md](projectneed.md)。范围收窄时同步"不做"表并写明原因。

## 2. 决策（本体系的核心动作）

只要出现"考虑过 A 和 B，选了 A 否了 B"，**当场**建一条 ADR：

```bash
cp docs/templates/adr.md docs/decisions/000X-<短名>.md
```

- 备选方案表和否决理由不能省，否则这条记录没有价值。
- 写"复查条件"：什么情况下这条决策该重估。
- 已经生效的 ADR 不改正文，推翻它就新开一条并把旧的标 `已废弃`。

时机要求很硬：决策理由大多来自对话，隔一天就忘了，事后补写出来的只会是结论，不是理由。

## 3. 设计

结论稳定后写进 `design/`，头部注明依据哪条 ADR。设计文档只写定论，讨论过程留在 ADR 里。

## 4. 编码与提交

标题一律 `<type>(<scope>): <subject>`。type 与 scope 用小写英文，subject 用中文说清做了什么。

| type | 什么时候用 |
| --- | --- |
| `feat` | 新增对外可见的功能 |
| `fix` | 修 bug |
| `docs` | 只动文档（`docs/**`，含根目录 `AGENTS.md` / `README.md`）或代码注释，不改运行行为 |
| `refactor` | 不改外部行为的结构调整 |
| `perf` | 只为更快或更省 |
| `test` | 只动测试 |
| `build` | 构建系统、依赖、打包（`Makefile` / `go.mod` / `Gradle` / `deploy/`） |
| `ci` | 持续集成配置 |
| `chore` | 以上都不是 |
| `revert` | 回滚某个提交 |

- scope 取本项目的模块名：<按实际填，例如 `api` / `store` / `cli`>。其中 `docs` 作 scope 只指 `docs/` 里的内容，根目录文档不算。跨多模块或纯仓库级改动就省略括号——省略的只是括号，type 仍照上表判，不等于自动落 `chore`。
- 标题 ≤ 50 字符，句末不加句号。禁止 `update`、`修改`、`临时`、`WIP`、`fix bug` 这类空词——写了等于没写。
- 破坏性变更在 type 后加 `!`（`feat(<scope>)!: ...`），并在正文末尾单独一行写 `BREAKING CHANGE: <改了什么、调用方怎么迁移>`。
- 正文：标题空一行之后写**为什么**，不复述 diff；每行 ≤ 72 字符。改的动机、非显然的取舍、踩过的坑写在这里，不写进代码注释。
- 正文最后一行必须是验证口径：`验证：<本项目的检查命令，如 make vet && make test> 全过（实测）`。没验证就照实写 `验证：未编译（本机无 SDK）`——藏起来比写出来更糟。
- footer 各占一行，可选：`ADR: 0003`（该提交依据的决策编号）、`Fixes: #12`、`Co-authored-by: 名字 <邮箱>`。

完整形状：

```
feat(<scope>): 离线操作改为服务端补交

补交逻辑收到服务端，客户端只负责排队，
这样换机之后队列不会跟着本地存储一起丢。
首版不做冲突合并，后写覆盖先写。

验证：make vet && make test 全过（实测）
ADR: 0003
```

- 一个提交对应一个能自证完整的改动；文档更新可以和代码同提交，但**不要**把文档更新留到"以后一起补"。
- 分支命名、评审要求：<按项目实际情况填。单人开发可直接提交主干；多人协作写清分支模型和评审要求>

## 5. 重构

先在 `refactor/` 写方案（新旧对比、迁移步骤、回滚方式），确认后再动手。改完把结论沉淀到 `design/`，并在 ADR 里记一次"为什么这样拆"。

## 6. 收尾（必做，无例外）

1. 更新 [NOW.md](NOW.md)：在做什么、下一步、断点状态、`> 更新：` 时间。
2. 新增/改名/删除过任何 md → 手工同步 [INDEX.md](INDEX.md) 的清单表，一行「链接 + 状态 + 说明」，状态和说明照抄该文档头部的两行。
3. 发现文档与代码不一致 → 立刻改文档或标记 `待复审`，别留着。

## 文档更新对照表

| 触发事件 | 文件 | 新建还是更新 |
| --- | --- | --- |
| 有方案被否掉 | `decisions/NNNN-*.md` | 新建 |
| 推翻旧决策 | 新 ADR + 旧 ADR 状态行 | 新建 + 微调 |
| 模块/表/接口定下来 | `design/<主题>.md` | 更新 |
| 需求范围变化 | `projectneed.md` | 更新 |
| 要重构某块 | `refactor/<主题>.md` | 新建 |
| 阶段/排期确定 | 由 `templates/milestone.md` 建 | 新建 |
| 故障、踩坑 | 由 `templates/incident.md` 建 | 新建 |
| 文档增删改名 | `INDEX.md` | 手工更新清单表 |
| 会话结束 | `NOW.md` | 更新 |
